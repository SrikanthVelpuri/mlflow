Chapter 1 — Storage layer

The data plane. Three concerns: where rows go (tracking store), where bytes go (artifact backends), and how to log without slowing down training (the async queue).

The store pattern

The contract that makes everything else portable. AbstractStore in mlflow/store/tracking/abstract_store.py defines about thirty operations: create_experiment, search_runs, log_batch, get_metric_history, record_logged_model, etc. New backends only need to subclass this — the REST API and the Python client do not change.

One interface, three (or more) backends. The same client code runs against all of them; the URI you set decides the implementation.

Three layers — fluent, client, store

The tracking surface is intentionally a thin pipeline. The fluent API is convenient but optional: every fluent call has a direct equivalent on MlflowClient. Internally the fluent module just looks up the active run id from a thread-local and calls the client.

Every log_* call traverses these layers. Each is a thin shim over the next.

The store contract

AbstractStore defines the operations every backend must implement. FileStore writes one YAML/JSON file per entity — good for laptops and CI, awful for concurrent writes. SqlAlchemyStore is the production backend — it owns the schema (SqlExperiment, SqlRun, SqlMetric, SqlParam, SqlTag, etc.) and uses Alembic migrations under mlflow/store/db_migrations/.

Schema essentials

The five tables that carry 90% of traffic:

experiments      (experiment_id, name, artifact_location, lifecycle_stage, ...)
runs             (run_uuid, experiment_id, user_id, status, start_time, end_time, ...)
metrics          (run_uuid, key, value, timestamp, step)        -- append-only, indexed (run_uuid, key, step)
params           (run_uuid, key, value)                          -- write-once
tags             (run_uuid, key, value)                          -- mutable
Common pitfall

People forget metric history is a per-step append. A 100-epoch training that logs 30 metrics per step writes 3,000 rows. A daily cron that re-logs the same metric 1,440 times is normal. Plan for that — and enable the async logging queue.

Roundtable — Why not Mongo / DynamoDB / Cassandra?
A Architect
The shape of our queries is relational: filter runs by experiment, join to metrics, sort by created. WHERE experiment_id = ? AND status = 'FINISHED' ORDER BY start_time DESC is the hot path. SQL with a few indexes is hard to beat there.
D Storage
DynamoDB would force us to invent secondary indexes for every search facet (status, run_name, tag value). And metrics are append-heavy time series — that wants either a relational table with the right composite key (run_uuid, metric_key, step) or a true time-series store. We picked the cheaper choice.
S SRE
Postgres is operational table stakes everywhere. Every cloud has managed Postgres with PITR, replicas, and backup tooling. Adopting a NoSQL store would offload state but onboard a new oncall surface.
M ML Engineer
There is a future where metric history outgrows row-per-point storage. At one customer we hit 80M rows in metrics in three months. That's where you want a Timescale/Druid/Influx side-car — but as a partition off SQL, not a rewrite.
A Architect
Right — and the AbstractStore boundary is exactly where you'd insert it. The "compose a metric store under SqlAlchemyStore" play is a six-month project, not a six-quarter one. That's the value of the contract.

Artifact backends

Models, plots, datasets — anything that's a file — land in an artifact repository, picked by URI scheme. Same store-pattern dance, applied to bytes instead of rows.

SchemeImplementationNotes
file:// / local pathLocalArtifactRepositoryDev. Don't ship.
s3://S3ArtifactRepositoryMost common. Boto3.
gs://GCSArtifactRepositorySame shape, different SDK.
wasbs:// / abfss://Azure reposBlob & ADLS Gen2.
dbfs:/ / databricks://DBFS / Unity CatalogTightly integrated; UC adds governance.
r2:// / http(s):// / ftp:// / sftp://Edge casesReal, but rare.

The contract every backend honors

class ArtifactRepository(ABC):
    def log_artifact(local_file, artifact_path=None): ...
    def log_artifacts(local_dir, artifact_path=None): ...
    def list_artifacts(path=None) -> list[FileInfo]: ...
    def download_artifacts(artifact_path, dst_path=None) -> str: ...
    def delete_artifacts(artifact_path=None): ...

Five methods. That's the entire surface a new backend has to implement.

Roundtable — Picking the right artifact backend
N Data Scientist
I just want my notebook to log_artifact("plot.png") and find it later. Anything that needs IAM JSON ahead of time is a non-starter for prototyping.
X Security
"Anything that doesn't need IAM" is also "anything that has no audit log." You want server-side encryption, bucket policies that block public ACLs, and CloudTrail on read. Pick a backend the security team has tooling for.
S SRE
For multi-region resilience, S3 with cross-region replication is the de-facto answer. GCS multi-region buckets are cleaner if you're on GCP. DBFS is fine if you're a Databricks shop, but consider that you've now coupled two systems' uptime.
D Storage
One quiet thing: artifact downloads during serving are on the hot path. If the model server is in us-east-1 and the bucket is in eu-west-2, your cold-start latency just bought a transatlantic round trip. Co-locate or pre-warm.
M ML Engineer
For air-gapped deployments, MinIO speaks the S3 API and slots into S3ArtifactRepository unchanged. For the on-prem question, that's the answer most of the time.

The async logging queue

Synchronous logging is a footgun for any tight training loop. AsyncLoggingQueue (in mlflow/utils/async_logging/) buffers calls and flushes them with log_batch — one round-trip per N points instead of N round-trips.

Why it's there

  • Training loop stays at training-loop speed.
  • Network blips don't block fit().
  • Backend gets batched writes — friendlier to Postgres.

What it costs

  • Last-second metrics can be lost on a hard crash.
  • Memory growth if the worker thread starves.
  • UI sees data with a small lag.
Design

Flushed on end_run and at interpreter exit (via atexit). Per-run queue with a single worker; on shutdown, the queue drains synchronously so completed runs commit cleanly. Failures during a flush bubble up as warnings — they do not crash training.
