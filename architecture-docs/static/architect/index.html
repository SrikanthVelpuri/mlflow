The architectural thesis

Most ML platforms accumulate by accretion: a tracking tool, a registry, a model server, a feature store, a tracing tool — six things, six APIs, six contracts. MLflow's bet is the opposite. One contract, many backends, many domains. The same store interface persists a sklearn run and an Anthropic LLM trace. The same scoring server hosts an XGBoost model and a multi-step agent. The same registry pins a fine-tuned transformer and a 1990s linear regression to a "champion" alias.

The architectural moves that make this possible are small and repeated:

  • An AbstractStore interface for every persistent thing (tracking, registry, artifacts).
  • A URI scheme registry so the right backend is chosen by the URI you pass.
  • A flavor pattern so every framework adapter exposes the same trio of save_model / log_model / load_model.
  • A universal pyfunc loader so anything callable becomes predict(x).
  • safe_patch as the single mechanism for both autologging and auto-tracing.
Architect's mantra

Don't add a noun without first asking which existing noun it can become. Trace became a sibling of Run, not a parallel system. ChatModel became a subclass of PythonModel, not a new package. The discipline of "minimum new concepts" is what keeps the surface area shippable.

The primitives, visualised

Every line of code in this repo serializes, queries, exports, or routes one of these. Five of them belong to the original ML platform; the sixth (Trace) is the GenAI extension and is a sibling of Run, not a child.

The six primitives. Solid arrows = ownership / parent-child. Dashed arrow = sibling: a Trace lives at the same level as a Run, both owned by an Experiment.

Why so few primitives?
A Architect
Every new noun multiplies the surface: REST endpoints, SDK methods, UI tabs, docs, RBAC scopes. Six is already pushing it. We absorbed traces into the run-shaped storage rather than making them a parallel domain.
D Storage
From my side, fewer primitives means fewer tables to migrate. SqlAlchemyStore only has to know about runs, metrics, params, tags, registered models, model versions, and now traces and spans. Any feature that doesn't fit there forces a schema change.
P PM
Users don't think in primitives, they think in tasks: "I want to compare two prompts." We can deliver that on top of three primitives (Trace, Assessment, Run) without growing the data model — that's the leverage.
