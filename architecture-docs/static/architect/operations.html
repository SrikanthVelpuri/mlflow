Chapter 6 — Operations & build-vs-buy

The non-functional concerns that decide whether the platform survives contact with reality. Multi-tenancy, cost, observability, and an honest comparison with the alternatives you might pick instead.

Multi-tenancy and isolation

MLflow OSS doesn't ship multi-tenancy as a primitive — it ships experiments as the natural unit of isolation. How you turn that into "team A can't see team B's runs" is a deployment-layer choice.

ApproachProsCons
One MLflow server per team Hard isolation. No accidental cross-reads. N tracking servers to operate. No global view.
One server, one DB, RBAC at the proxy Single pane of glass. Centralised ops. Auth lives outside MLflow — proxy has to enforce per-experiment ACLs.
One server, schema-per-tenant Hard data isolation, single deploy. Custom store layer needed; not stock OSS.
Databricks-managed (MLflow on Unity Catalog) RBAC, lineage, encryption baked in. Vendor lock to Databricks.
Roundtable — Building multi-tenancy on OSS MLflow
A Architect
The pragmatic OSS path: one server, OIDC at an ingress proxy, experiment naming convention {team}/{project}, and a server-side filter that rejects requests reading other teams' experiments. Coarse, but ships in a sprint.
X Security
"Convention plus proxy filter" is fine for trust-but-verify orgs. For regulated workloads (HIPAA, SOC2 with hard data segregation), one server per tenant — no shortcut.
S SRE
If you go single-server, plan for the noisy-neighbour problem. One team's hyperparameter sweep can saturate the async log queue and starve everyone. Per-team rate limits at the ingress.

Cost & observability

The cheapest hour you'll ever spend on this platform is wiring up the operator's view: which team is generating which load, how big is the tracking DB, how much S3 are we burning, what's the LLM cost per agent.

What to monitor

  • Tracking DB: row counts on metrics, params, tags, traces, spans; query p95 on search_runs; index bloat.
  • Artifact storage: bytes per experiment, top-N largest models, cold-tier eligibility.
  • Scoring server: p50/p95/p99 latency per model URI; signature validation rejection rate.
  • AI Gateway: tokens-in / tokens-out / cost per route, per-team; rate-limit rejection rate; provider 5xx and timeout rate.
  • Traces: span depth distribution; top-cost agents; tool-call frequencies.
The cost trap

Two patterns sneak up on bills: (1) people log_artifacting whole datasets every run instead of pointing at a Dataset reference; (2) chatty agents that loop over tools and rack up gateway calls without circuit-breakers. Build alerting for "cost per run" and "cost per trace" early — it's easier than retroactive cleanup.

Roundtable — When NOT to pick MLflow
P PM
If we have three data scientists and no platform team, hosted W&B is faster to value. The day the company has 30 people doing ML, the calculus inverts.
A Architect
If we're an LLM-only shop with no classical ML pipeline, LangSmith + a thin model registry is a more focused stack. We'd lose MLflow's flavor breadth — but we don't use it.
S SRE
If we're already on SageMaker for serving and don't need cross-cloud portability, the gravitational pull of one ecosystem wins. Mixed-cloud orgs are where MLflow's pluggability earns its keep.
M ML Engineer
If we're just versioning models and don't need experiment tracking or tracing, DVC + a git-based deploy is leaner. MLflow is overkill for "I have one notebook and one prod model."

Closing thought

Architecture is the discipline of what you don't add. The reason MLflow's GenAI surface didn't double the codebase is that almost every new capability extended an existing primitive. When you're tempted to add a new noun, ask which existing one it can become. That single habit will save more than any framework choice.
