Chapter 2 — Packaging & registry

How a trained sklearn estimator and a fine-tuned transformer end up loadable through the same one-line API. The MLmodel format, the flavor pattern, and the registry that pins versions to mutable named pointers.

The MLmodel file

Every saved model directory contains a YAML manifest:

artifact_path: model
flavors:
  python_function:
    loader_module: mlflow.sklearn
    model_path: model.pkl
    env: conda.yaml
  sklearn:
    sklearn_version: 1.4.0
    serialization_format: cloudpickle
signature:
  inputs: '[{"name": "age", "type": "long"}, ...]'
  outputs: '[{"type": "double"}]'
run_id: 9f...

flavors is a dict of overlapping representations of the same model. Almost every native flavor also registers a python_function flavor — that is the universal entry point for serving and tools.

Flavors — the framework adapter contract

A flavor is a Python module that knows how to serialize and deserialize one framework. Every flavor exports the same trio:

def save_model(model, path, signature=None, input_example=None, ...): ...
def log_model(model, artifact_path, ...) -> ModelInfo: ...
def load_model(model_uri, ...): ...
Every framework's model collapses through the MLmodel manifest into one universal callable. Tools downstream (serving, eval, deploy) only know pyfunc.

Native flavors in this repo (28+)

  • Classical ML: sklearn, xgboost, lightgbm, catboost, prophet, statsmodels, spacy, mleap, onnx, paddle, h2o, pmdarima, fastai, diviner, shap
  • Deep learning: pytorch, tensorflow, keras
  • Spark: spark, pyspark.ml
  • GenAI: transformers, langchain, llama_index, dspy, openai, bedrock, anthropic, gemini, groq, crewai, autogen, sentence_transformers, litellm, promptflow
  • Universal: pyfunc

Signatures and schemas

mlflow/models/signature.py defines ModelSignature (input + output + params schemas) using Schema, ColSpec, and ParamSchema from mlflow/types/schema.py. Signatures are inferred from input_example whenever possible. They are enforced at serving time by the scoring server, which is what makes pyfunc safe to expose over HTTP.

Why always pass a signature

Without one, malformed payloads either silently produce wrong outputs or crash inside the model — neither is debuggable. With one, the scoring server returns a 422 with a precise error before the model is invoked. It's also what enables the UI's "predict" button and the lineage tools.

Roundtable — Why YAML, why pickle, why pyfunc?
A Architect
YAML for MLmodel because humans read it during incidents. The whole file fits on one screen; you can grep it in S3. JSON would have worked, but YAML's comments and multi-line strings ergonomics matter when the file is auditable surface.
X Security
Pickle is a known footgun — it executes code on load. We accept it because it's how Python ML serialization works in practice. The mitigation is that a registered model is only loadable from a trusted artifact location — a deployment policy, not a code-level guarantee.
M ML Engineer
For the compliance-strict crowd: ONNX or SavedModel as the primary serialization, pickle as the fallback for stuff that doesn't graph-export. The flavor lets us record both — and on load, prefer the safe one.
A Architect
pyfunc is the universal flavor because it's the smallest contract: a class with predict(context, model_input). Every native flavor also registers a python_function entry pointing at its loader. Tools (serving, eval, deploy) only need to know pyfunc — they don't care if the underlying thing is sklearn or PyTorch or Anthropic.

The Model Registry

Same store pattern as tracking, different domain. RegisteredModel holds a name and tags; ModelVersion is an immutable snapshot pointing at a tracked model artifact, identified by an auto-incrementing integer per registered model.

Stages vs aliases — the migration

Stages (legacy)Aliases (new)
CardinalityFixed enum: None, Staging, Production, ArchivedArbitrary: champion, challenger, shadow, eu-prod, ...
MutabilityOne stage per version, one version per stageMany aliases per version, alias points at one version
Decoupled from lifecycle?No — implies promotion ladderYes — semantics are yours
RecommendationAvoid in new workflowsDefault for everything new
Aliases are pointers; promotion is a metadata flip. Code consumers always read models:/churn-classifier@champion — never a version number.
Roundtable — Why aliases beat stages
P PM
Stages assumed everyone wanted the same lifecycle: dev → staging → prod. We had teams running A/B with three live versions, regional rollouts, dark launches — none of that maps to a four-state ladder.
A Architect
Aliases are pointers; stages were states. Pointers compose: models:/churn@champion reads cleanly in code, in dashboards, and in Helm values. We can also promote by re-pointing without copying bytes.
M ML Engineer
The migration headache is real though: every Airflow DAG and every models:/X/Production URI needs to switch. We deprecate stages but keep them queryable indefinitely — Hyrum's Law applies.
X Security
Aliases need RBAC. "Anyone who can update champion can deploy to prod" is a real privilege escalation if you're not careful. Lock down alias write per environment.

What to put in version description & tags

  • Description: the why — "rolled in zip-code one-hot, fixed leak from last_login".
  • Tags: data_version, git_sha, training_run_id, approved_by, compliance_review_id.
