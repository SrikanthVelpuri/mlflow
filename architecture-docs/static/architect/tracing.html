Chapter 4 — Tracing & auto-tracing AI

The new foundation for the GenAI surface. A trace data model that's a sibling of Run, a private TracerProvider that doesn't collide with the user's OTel stack, and the safe_patch pattern that auto-instruments 14+ LLM SDKs without changing user code.

The trace data model

Defined in mlflow/entities/span.py and mlflow/entities/trace*.py.

TypeDescription
SpanTypeEnum: LLM, CHAT_MODEL, CHAIN, AGENT, TOOL, RETRIEVER, EMBEDDING, RERANKER, PARSER, UNKNOWN
LiveSpanA mutable span currently being recorded (start, set attribute, end, set status, set events).
SpanThe immutable, persisted form of a LiveSpan.
Trace(TraceInfo, TraceData) — header metadata plus the full span list.
TraceInfoIdentifies the trace: request_id, experiment_id, timestamp_ms, execution_time_ms, status, tags.

A Trace is logically a single root span and the tree underneath it; serialised, it is a flat span list plus header.

The trace pipeline

mlflow/tracing/trace_manager.py holds an in-memory buffer keyed by request_id. Spans are appended as they end; when the root span ends, the manager finalises the Trace and exports it.

Left: where spans are produced. Middle: where they're buffered and assembled. Right: where they're shipped. The TraceManager owns the lifecycle; exporters are pluggable.

Why a private TracerProvider?

MLflow does not use the global OpenTelemetry tracer provider. mlflow/tracing/provider.py creates and owns a private TracerProvider so MLflow's instrumentation does not collide with another OTel-using library running in the same process — PromptFlow, Snowpark, the user's own observability stack.

Roundtable — Why a private TracerProvider?
A Architect
If we used the global provider, two libraries calling set_tracer_provider would race. The user's own OTel exporter would either eat our spans or crash on our schema. A private provider is the only way to be a polite citizen.
G AI Engineer
Practical upside: you can run MLflow tracing alongside Honeycomb, Datadog, or LangSmith. Each has its own span pipeline; ours doesn't pollute theirs.
S SRE
Downside: no automatic correlation with the user's existing distributed traces. If you want trace_id correlation across services, you have to wire it explicitly via context propagation.

Auto-tracing — the safe_patch pattern

Every LLM SDK or orchestration framework gets a flavor module that follows the same pattern:

  1. Patch the SDK's entry point with safe_patch from mlflow/utils/autologging_utils/safety.py.
  2. Open a span (type chosen by what the patched method does).
  3. Convert provider-specific messages to MLflow's ChatMessage/ChatTool schema.
  4. Run the call, capture result, token usage, errors.
  5. Close the span: status, attributes, output messages, finish reason.
unchanged Invariants: user's call always runs · user's exception always propagates unchanged · instrumentation failures only WARN
The contract that makes monkey-patching safe in production. Tracing failures are observable but never destructive to the user's code path.

Why monkey-patching

  • Zero user code change — installation is the activation.
  • Works for SDKs we don't own and can't get a callback hook on.
  • safe_patch guarantees we never break the SDK if our handler raises.

What it costs

  • Brittle to SDK upgrades — each release of OpenAI/Anthropic can move the surface.
  • Subclass-shadowing edge cases (Swarm, custom Runnables).
  • Some SDKs offer real callback hooks (LangChain, LlamaIndex) — we use those instead.

Unified chat schema

Every auto-tracing adapter converts to a single chat schema so that the UI, evaluation, and downstream consumers don't have to know which provider produced a span. The schema lives in mlflow/types/chat.py and mlflow/types/llm.py:

  • ChatMessage — role, content (text or multi-modal parts), tool_calls, tool_call_id, name.
  • ChatTool — function-calling schema (name, description, parameters JSONSchema).
  • ChatParams — temperature, max_tokens, top_p, top_k, frequency_penalty, presence_penalty, stop, tools, tool_choice, metadata.
  • ChatCompletionResponse / ChatCompletionChunk — list of ChatChoices plus model and usage metadata.

Intentionally OpenAI-shaped because that's the closest thing to a de facto standard. Every other provider gets a converter in its flavor module (e.g. mlflow/anthropic/chat.py).

Roundtable — When monkey-patching is the right choice
G AI Engineer
For SDK observability, the alternative is a wrapper SDK ("from mlflow_openai import OpenAI"). That breaks the user's existing code. Monkey-patching keeps from openai import OpenAI working — a much smaller migration tax.
X Security
Monkey-patching means our code runs inside the user's process for every LLM call. Our error path must be airtight — that's what safe_patch is for. Any exception in tracing should be caught and logged at WARN, never propagated.
M ML Engineer
For LangChain we use the real callback handler interface — LangchainTracer. Where SDKs offer first-class observability, take it. Monkey-patching is the fallback, not the goal.
