Chapter 3 — Projects & serving

Where models become endpoints. The MLproject runner for reproducible training, the pyfunc scoring server for inference, and the deployment plugin interface for managed targets.

Projects — reproducible runs

MLproject declares: a name, an environment (conda.yaml / Docker image / python_env.yaml / Databricks job spec), and entry points (named commands with typed parameters). Backends in mlflow/projects/backend/ implement the same run_project for local, Docker, K8s, and Databricks targets.

name: churn-training
python_env: python_env.yaml
entry_points:
  main:
    parameters:
      data_uri: {type: str}
      n_estimators: {type: int, default: 200}
      max_depth: {type: int, default: 8}
    command: "python train.py --data {data_uri} --n-est {n_estimators} --depth {max_depth}"
Roundtable — Is "Projects" worth the seam?
A Architect
Projects predates the modern world of Airflow / Argo / Dagster / Prefect. Every shop already has an orchestrator. Where Projects still pays off is the "reproducible single run" promise — a researcher hands over an MLproject and CI can re-run it.
M ML Engineer
In practice we use it for the inner loop (run my training in Docker with parameters) and Airflow for the outer loop (sweep, retrain, redeploy). They aren't competitors.
P PM
Marketing-wise it's our reproducibility story. Practically it's an entry-point definition that researchers actually fill in.

The pyfunc scoring server

mlflow/pyfunc/scoring_server/ is the Flask WSGI app that turns any logged pyfunc model into an HTTP endpoint:

GET  /ping       # readiness
GET  /health     # health
GET  /version    # MLflow + model versions
POST /invocations
  body: dataframe_split | dataframe_records | instances | inputs
  → signature validation → pyfunc.predict() → JSON

Multiple payload shapes are accepted on purpose: instances/inputs match TensorFlow Serving and SageMaker conventions; dataframe_* matches MLflow's own.

Request lifecycle. Note the early-reject path: signature validation rejects malformed payloads with a 422 before the model is invoked.

The deployment plugin interface

mlflow/deployments/ defines BaseDeploymentClient with one method per lifecycle action: create_deployment, update_deployment, predict, list_endpoints, delete_deployment. The plugin_manager.py discovers third-party deployment targets via Python entry points.

Roundtable — Picking a serving runtime
N Data Scientist
Just mlflow models serve on my laptop is a perfect 80% case for me. I want zero-config to validate that my signature works end-to-end.
M ML Engineer
For low-latency single-model serving on GPU, the scoring server is fine but you'll outrun it: it's Flask + threaded WSGI, no batching, no GPU mem management. Triton or TorchServe with a thin pyfunc adapter is the next step.
S SRE
Operationally, "MLflow scoring server in a container behind a managed load balancer + HPA" is fine for ~99% of workloads. Pin the model URI at build time so the container is immutable; never resolve aliases at request time on production traffic.
A Architect
For LLM/agent workloads you almost certainly want a separate path — they're long-lived, streaming, and they fan out to providers. That's exactly what the AI Gateway covers. Don't try to make scoring server do streaming SSE for a chat model; reach for a purpose-built runtime.
X Security
Whatever the runtime: the scoring server has no auth by default. Never expose it to the public internet without a gateway in front. Same advice for the tracking server.
Production rule

Pin the model URI at container build time. models:/X@champion is great for callers, but the running pod should bake in the resolved models:/X/4 — otherwise an alias flip can hot-swap a model under live traffic without a deploy event, breaking your "every change is observable" property.
