1. How to use this guide

  • Read concepts cold. Try to define each one without peeking. If you can't, that's the section to study.
  • Answer Q&As out loud before opening the answer. The pause where you think is the actual practice.
  • For system design, draw before reading. Spend 15 minutes whiteboarding, then compare. The diff is the lesson.
  • Treat tradeoffs as the interview. Most senior platform interviews are about defending choices under "but what if..." pressure. Practice the second answer, not the first.
Interviewer tell

The mark of a senior candidate isn't knowing more facts; it's saying "it depends" and then naming the dimension it depends on. "It depends on how big your eval set is" is a senior answer; "it depends" alone is a junior one.

3. Warm-up questions

What problem does MLflow solve, in one sentence?

It gives you one platform — one client, one server contract, one set of primitives — for tracking experiments, packaging models, versioning them, serving them, and (in the GenAI surface) tracing and evaluating LLM calls; pluggable across backends so the same code runs on a laptop or in a cloud.

What are the five (or six) primitives?

Experiment, Run, Model, RegisteredModel/ModelVersion, Artifact — and Trace if you include the GenAI surface.

Why is pyfunc important?

It's the universal callable interface: any model from any flavor exposes predict(context, model_input). Tools (scoring server, evaluation, deployment) only need to know pyfunc; they don't care if the underlying model is sklearn, PyTorch, or an Anthropic-backed agent. It's the smallest contract that makes the rest of the platform polymorphic.

What's the difference between a stage and an alias on a model version?

Stage is a legacy four-state enum (None / Staging / Production / Archived) where each version sits in exactly one stage. Alias is an arbitrary mutable named pointer (champion, challenger, eu-prod) that you can attach to any version. Aliases are decoupled from a fixed lifecycle — you choose the semantics. New workflows should use aliases.

What goes in an MLmodel file?

A YAML manifest with: the artifact path, one or more flavors (each describing how to load), an optional signature (input + output schemas), an optional input_example, and the run_id. Almost every native flavor also writes a python_function flavor so the model is loadable through the universal pyfunc interface.

4. ML platform — deep dive Q&A

Walk through what happens when you call mlflow.log_metric("loss", 0.1).

The fluent API (mlflow/tracking/fluent.py) reads the active run_id from a thread-local. It calls MlflowClient.log_metric, which forwards to TrackingServiceClient.log_metric — the layer that translates Python calls into RPCs. From there it goes to the configured AbstractStore implementation. If async logging is enabled, the call is enqueued and a worker thread flushes batches via log_batch; otherwise it makes a direct call. The store implementation (SqlAlchemyStore in production) inserts a row into the metrics table indexed on (run_uuid, key, step).

Why does MLflow have an async logging queue, and what are the failure modes?

Synchronous round-trips to the store would dominate training time on tight loops that log thousands of points per second. The queue buffers calls and flushes them in batches, so the training loop runs at training-loop speed. Failure modes: on a hard process kill, the in-flight batch can be lost (the queue flushes on end_run and at atexit, but not on SIGKILL). The worker thread can also fall behind under sustained load, growing memory. Failures during a flush surface as warnings rather than crashing the training process.

How does MLflow stay framework-agnostic with 28+ flavors?

Two patterns. (1) The flavor contract: every framework module exports save_model / log_model / load_model with the same signature. (2) The pyfunc registration: nearly every native flavor also registers a python_function entry in the MLmodel manifest pointing at its loader. So tools downstream don't need to know about sklearn or PyTorch; they call mlflow.pyfunc.load_model(uri) and get something with predict.

How is the model registry related to the tracking store?

They're two separate stores with the same architectural pattern: an AbstractStore interface with FileStore and SqlAlchemyStore implementations. They can share a database in production. A ModelVersion in the registry points at a model artifact in the artifact repository, which was originally produced by a tracking Run — but the registry's lifecycle is independent of the run's. You can delete the run; the registered model version's artifact location is its own.

Why YAML for MLmodel and not JSON?

Practical reasons: humans read it during incidents (aws s3 cp ... - + read), comments are supported, multi-line strings are ergonomic, and it diffs cleanly. JSON would have worked technically; YAML's readability won. The schema is small enough that the YAML/JSON "ambiguity" pitfalls don't bite.

What's a model signature, and why should you always pass one?

A ModelSignature declares input + output + params schemas using Schema and ColSpec. The scoring server validates payloads against it before they reach predict. Without one, malformed payloads either silently produce wrong outputs or crash inside the model — neither is debuggable. With one, you get a 422 with a precise error. It's also what enables the UI's "predict" button and lineage tools.

How would you scale the tracking server to 1,000 users?

The MLflow server is stateless Flask; horizontal scaling is straightforward — N replicas behind an LB. The bottleneck is the database. Concrete steps: (1) move from SQLite/FileStore to Postgres; (2) ensure indexes on (run_uuid, key, step) for metrics, on experiment_id for runs, on (run_uuid, key) for params/tags; (3) PgBouncer for connection pooling; (4) a read replica for the UI's search_runs traffic; (5) consider archiving old metric history to a cold table or time-series store; (6) per-team rate limits at the ingress to prevent noisy-neighbour. The async logging queue on clients also helps — it batches writes.

Why is the artifact repository separate from the tracking store?

Different access patterns and different durability/cost profiles. Tracking data is row-shaped, queryable, indexed — that's a database. Artifacts are bytes — sometimes gigabytes — that you read sequentially and rarely; that's blob storage. Co-locating them would either bloat the database or force the blob store to support querying. The split also lets you swap the artifact backend (S3 ↔ GCS ↔ Azure ↔ DBFS) without touching tracking.

What does "store pattern" buy MLflow architecturally?

Three things. (1) Portability: same client API works on a laptop (FileStore), in production (SqlAlchemyStore), and against a remote server (RestStore). (2) Pluggability for new backends: someone can write a DynamoDBStore subclass without touching the REST API or Python client. (3) Testability: every higher layer can be tested against an in-memory or file-backed store.

Walk me through the request path of POST /invocations on a deployed sklearn model.

(1) Container starts; mlflow models serve -m models:/X@champion resolves the alias to a version, downloads the artifact dir from S3, and starts the Flask scoring server. (2) Request arrives; the server unmarshals one of the supported payload shapes (dataframe_split, dataframe_records, instances, inputs) into a pandas DataFrame. (3) The DataFrame is validated against the signature — wrong types or missing columns fail fast with a 422. (4) pyfunc_loaded.predict(df) is invoked; the pyfunc wrapper delegates to the sklearn flavor's loader, which calls estimator.predict(df). (5) The result is serialised back to JSON.

5. AI / GenAI platform — deep dive Q&A AI

What is a Trace and how does it relate to a Run?

A Trace is a tree of typed Spans capturing one logical LLM/agent invocation. It's stored in the same tracking store as runs and queryable through the same REST API, but it's a sibling of Run, not a child. A Run might capture a training execution; a Trace captures one inference call to a model. Conceptually: Trace : Run :: Span : Metric — both observations, but Span is hierarchical and time-stamped where Metric is a single numeric point.

Why does MLflow use a private OpenTelemetry TracerProvider instead of the global one?

To be a good citizen in processes that already use OTel for their own observability — think PromptFlow, Snowpark, or the user's own distributed tracing. If MLflow installed itself as the global provider, it would either get clobbered by the user's stack or clobber theirs. The private provider in mlflow/tracing/provider.py is isolated; spans flow through MLflow's own pipeline and exporters. The downside is no automatic correlation with the user's existing distributed traces — that has to be wired explicitly.

How does auto-tracing for OpenAI work under the hood?

The mlflow/openai/ flavor uses safe_patch from mlflow/utils/autologging_utils/safety.py to monkey-patch OpenAI.chat.completions.create, OpenAI.completions.create, and OpenAI.embeddings.create. The wrapper opens an LLM-typed span, converts the request to MLflow's ChatMessage/ChatTool schema, runs the original call, captures the response and token usage, and closes the span with status, attributes, and output messages. safe_patch ensures any exception in the wrapper is caught and logged at WARN — never propagated to the user's code.

Why convert every provider's messages to a single chat schema?

So that the UI, evaluation tools, and downstream consumers don't have to know which provider produced a span. A single ChatMessage shape lets you compare "the call to OpenAI" with "the call to Anthropic" with "the call to Bedrock" in the same view, run the same safety judge over all three, and migrate between providers without rewriting consumers. The schema is OpenAI-shaped because that's the closest thing to a de facto standard; every other provider gets a converter in its flavor module.

Why is ChatModel a subclass of PythonModel rather than a parallel class?

So agents inherit the entire ML platform's machinery for free: tracking, registry, signatures, scoring server, deployment plugins. A ChatModel is just a typed PythonModel with predict(context, messages, params) -> ChatCompletionResponse. The same Helm chart that deploys a churn classifier deploys a multi-turn agent. The same models:/X@champion URI works for both. This is the architectural thesis: don't build a parallel system.

What does the AI Gateway actually do?

It's a server in front of provider APIs that solves three things: (1) Provider lock-in — code calls a stable endpoint name (my-chat) and the gateway routes to OpenAI, Anthropic, Bedrock, etc. by config. (2) Credentials — provider keys live in the gateway, not in app code or notebooks. (3) Governance — rate limits, request queuing, audit logging are centralised. Routes are typed (chat, completions, embeddings); each provider has an adapter under mlflow/gateway/providers/.

How does GenAI evaluation differ from classical ML evaluation?

Classical eval is "compute these metrics on this holdout set" — deterministic, numeric, ground-truth-based. GenAI eval has to handle non-deterministic outputs and often-absent ground truth. The MLflow model: each row produces Assessments (per-row scores from heuristics, LLM-as-judge, or humans) which aggregate into metrics. Crucially, every LLM call inside the eval is itself traced — the judge's call leaves a trace, the agent's calls leave traces, and assessments link back by request_id. The eval UI surfaces a low-scoring row one click away from the trace that produced it.

When is LLM-as-judge a bad idea?

Three cases. (1) Factual correctness without ground truth — you're outsourcing to the same class of error. (2) High-stakes domains (medical, legal, safety-critical) — judges have hallucinations too. (3) Highly adversarial inputs — prompt injection in the input being judged can flip the judge's verdict. Mitigations: pair LLM-as-judge with heuristic judges, calibrate against a human-rated set quarterly, and never let user input control the judge's role (use system prompts and structured templates).

Why is auto-tracing built on monkey-patching rather than wrapping?

If we shipped a wrapper SDK ("from mlflow_openai import OpenAI"), every user's existing code would have to change to get observability. Monkey-patching keeps from openai import OpenAI working — observability is an installation, not a refactor. The cost is brittleness to SDK upgrades and complexity in safe_patch to ensure errors in our handler don't propagate. Where SDKs offer first-class callbacks (LangChain, LlamaIndex), MLflow uses those instead — patching is the fallback.

What happens end-to-end when a user calls a deployed ChatModel agent?

(1) The serving endpoint receives POST /invocations with a chat payload. (2) The pyfunc scoring server validates against the ChatModel signature. (3) _ChatModelPyfuncWrapper deserialises into typed ChatMessages, opens a root AGENT span, calls predict. (4) Inside predict, every LLM call made through an instrumented SDK is auto-traced — each becomes an LLM span under the agent root. (5) Tool calls become TOOL spans; retrieval steps RETRIEVER. (6) The agent returns a ChatCompletionResponse; the wrapper closes the root span; the TraceManager finalises and ships to the configured exporter. (7) The trace lands in the same experiment as the run that registered the agent. Same primitives, all the way down.

6. System design prompts

For each: spend 15 minutes whiteboarding before reading. Score yourself on whether you covered the same dimensions, not whether you reached the same answer.

6.1 Design an ML experiment tracking system

Show solution outline

Requirements to surface: 1k engineers, ~1M runs/year, ~1B metric points, sub-second query for "show me last 10 runs in this experiment", offline read for dashboards, multi-region.

Components:

  • Stateless API tier (Flask/FastAPI) behind LB; horizontal scale.
  • Primary store: Postgres. Tables: experiments, runs, metrics, params, tags. Compound index (run_uuid, key, step) on metrics.
  • Async ingestion path: client-side batching queue + server-side bulk insert. Optionally Kafka in front of writes for very high QPS.
  • Artifact store: S3 (or equivalent), URI-routed; co-located with serving region.
  • Read replica for UI/list queries. Hot run reads from primary, list/search from replica.
  • Cold tier: archive metric history older than retention to a partitioned table or Parquet on object storage.
  • Auth: SSO at ingress; per-experiment ACLs.
  • Observability: per-team write rate, query p95, table sizes, async-queue depth.

Tradeoffs to discuss when prompted: SQL vs NoSQL (queries are relational, pick SQL); per-team server vs shared (operational burden vs noisy-neighbour); pluggable artifact backend (the URI scheme registry pattern).

6.2 Design an LLM observability platform

Show solution outline

Requirements: capture every LLM call across N services and M provider SDKs; queryable spans; cost attribution; PII safety; sampling for high QPS.

Components:

  • Auto-instrumentation per SDK: monkey-patch entry points, emit typed spans (LLM, TOOL, RETRIEVER, AGENT). Use first-class callbacks where the SDK offers them.
  • Unified chat schema as the wire format — all providers convert to it.
  • Private TracerProvider per process to coexist with the user's OTel.
  • TraceManager: in-memory buffer keyed by request_id; finalises trace when root span ends.
  • Exporters: a primary store (your tracking store), an OTel exporter for the user's own pipeline, optionally a cold exporter to object storage.
  • Sampling: 100% errors, 100% low-confidence, %-sampled successes.
  • PII masking: at the trace boundary; configurable per attribute.
  • Cost attribution: capture tokens_in/tokens_out/model per span; per-team / per-route aggregations.
  • Storage: span tables grow fast — plan TTL, hot/cold split, indexes on (experiment_id, request_id).

Tradeoffs: wrap vs patch (patch wins for adoption, costs brittleness); private vs global tracer provider; sampling strategies; cost of full PII vs minimal-attribute traces.

6.3 Design a model registry with safe promotion

Show solution outline

Requirements: versioned, immutable model artifacts; named promotions (champion, challenger, regional); RBAC tiered by environment; auditable; rollback in seconds.

Components:

  • RegisteredModel: name + tags + description.
  • ModelVersion: immutable, monotonically incrementing per registered model, points at an artifact URI.
  • Aliases: arbitrary string → version pointers; many aliases per version, one version per alias.
  • Alias write RBAC: shadow open; challenger requires team lead; champion requires on-call sign-off.
  • Audit log: every alias change is event-logged with actor, before/after.
  • Consumption convention: prod code never references version numbers; always models:/X@alias.
  • Rollback: a one-call API that flips the alias back to the previous version (recorded in audit).

Tradeoffs: stages vs aliases (cardinality, decoupling from lifecycle); copy bytes vs metadata flip on promotion (metadata flip wins for speed and rollback); RBAC at platform vs at gateway in front (platform-level avoids the per-team enforcement gap).

6.4 Design a unified inference gateway for multiple LLM providers

Show solution outline

Requirements: N providers, M client teams, unified URL, central key management, per-team rate limits and cost attribution, audit, low-latency.

Components:

  • Typed routes: chat, completions, embeddings — provider-agnostic schema in / provider-agnostic schema out.
  • Provider adapters: one per backend, mapping route schema to provider-specific calls.
  • Key management: keys in the gateway's secret store, never in clients. Rotate aggressively.
  • Per-team / per-route rate limits: token-bucket; clear 429 with Retry-After.
  • Idempotency: optional client request ID for retry safety.
  • Audit log: shipped to SIEM; keys never logged; payload PII configurable.
  • Cost attribution: count tokens in/out per call, attribute by team + route; surface in dashboards.
  • Reliability: timeouts, circuit breakers, optional fallback route on provider 5xx.
  • Caching (optional): exact-match or semantic cache, with care around staleness and PII.

Tradeoffs: single gateway region vs multi-region (latency vs blast radius); semantic cache (cost win, correctness risk); whether to do retry inside the gateway or push to clients.

6.5 Design an evaluation harness for an LLM agent

Show solution outline

Requirements: reproducible eval on a versioned dataset; multiple judges per row; LLM-as-judge plus heuristics plus humans; per-PR gate; explainable failures.

Components:

  • Eval set: in version control; rows are (input, optional_target, metadata).
  • Runner: invokes the agent on each row; captures the trace.
  • Judges: pluggable callables. Heuristic (regex, JSON validity, contains-keyword), LLM-as-judge (templated prompt against a strong model), human (UI for sampling).
  • Assessment storage: per-row, with name, value, rationale, source, error.
  • Aggregation: rolled into metrics (mean, p50, p95).
  • Trace linking: each assessment carries the agent's request_id; UI lets you jump from a low-scoring row to the trace.
  • Calibration: recurring job that compares LLM-judge against the human-rated subset; alarms on drift.
  • CI gate: per-PR re-run; fail on regression vs baseline above tolerance.

Tradeoffs: LLM-judge cost vs frequency (every PR is expensive on a 5k row set; sample); judge prompt brittleness; human judgement throughput as a bottleneck.

7. Behavioural & tradeoff questions

Tell me about a time you balanced velocity and reliability on a platform team.

Frame: name the conflict, describe the resolution mechanism (not the resolution itself), name the residual cost.

Example shape: "Our DS team wanted self-serve promotions; SRE wanted gated. We didn't pick one — we tiered: shadow alias was self-serve, champion required on-call sign-off, alias-write RBAC enforced it. The residual cost was that the tier had to be communicated explicitly; we wrote it into the runbook and the registry UI surfaced the policy. Outcome: time-to-shadow dropped to minutes; champion promotions stayed safe."

How do you decide between building a feature in the platform and pushing it to product teams?

Heuristic: if N teams will need it within 12 months and the abstraction is stable, platform owns it. If only one team needs it, or the abstraction is changing weekly, the team owns it. The cost of premature platformisation is locking in a wrong shape; the cost of late platformisation is N reinventions. Track which capabilities multiple teams have built — that's the signal.

A PM wants a feature that needs an unapproved LLM provider. What do you do?

Two parallel tracks. (1) Run the security/legal review in parallel with whatever development can happen on a sanctioned provider. (2) If the PM's deadline is binding, scope the feature to the sanctioned provider; ship something; revisit when the new provider is approved. The trap is treating "approved provider list" as immutable — make sure there's a path to add providers, with an SLA. The gateway makes the swap a config change.

A data scientist won't follow the eval-gate process. How do you handle it?

Find out why before enforcing. Common root causes: the eval is too slow (fix the runner, not the policy), the eval set is irrelevant to their model (let them PR new rows), the gate's failure messages are unhelpful (improve the diagnostics), or they don't understand the value (show them the last incident the eval would have caught). Enforcement without root-cause is theatre; the workaround surfaces somewhere else.

How do you justify the cost of the platform to a CFO?

Three numbers, framed as counterfactuals: (1) Engineer hours saved — how many hours would N teams spend reinventing tracking/registry/serving without it? (2) Incidents prevented — what's the production incident rate before vs after the eval gate, the signature requirement, the gateway's rate limits? (3) Provider cost reduction — what % did per-team gateway routing + sampling cut. Anchor every claim in a measurement, not a vibe.

Sketch safe_patch in pseudocode. 
def safe_patch(target_module, function_name, patch_function):
    original = getattr(target_module, function_name)

    @functools.wraps(original)
    def wrapper(*args, **kwargs):
        try:
            # <-- our pre-call instrumentation runs here
            patch_state = patch_function.before(args, kwargs)
        except Exception as e:
            log.warning("MLflow instrumentation pre-call failed", exc_info=e)
            patch_state = None

        try:
            result = original(*args, **kwargs)
        except Exception:
            try:
                patch_function.on_error(patch_state)
            except Exception as e:
                log.warning("MLflow instrumentation error-path failed", exc_info=e)
            raise  # re-raise the user's original exception unchanged

        try:
            patch_function.after(patch_state, result)
        except Exception as e:
            log.warning("MLflow instrumentation post-call failed", exc_info=e)

        return result

    setattr(target_module, function_name, wrapper)

Key invariants: the user's call always runs; the user's exception always propagates unchanged; our instrumentation failures only WARN. That's the contract.

Write a tiny ChatModel that calls Anthropic and returns a response. 
import mlflow
from mlflow.pyfunc import ChatModel
from mlflow.types.llm import ChatCompletionResponse, ChatMessage, ChatChoice
from anthropic import Anthropic

class MyAgent(ChatModel):
    def load_context(self, context):
        self.client = Anthropic()  # API key from env

    def predict(self, context, messages: list[ChatMessage], params):
        # convert MLflow ChatMessages to Anthropic message format
        anthro_msgs = [{"role": m.role, "content": m.content} for m in messages]
        resp = self.client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=params.max_tokens or 1024,
            messages=anthro_msgs,
        )
        # auto-tracing already records the LLM call; we just return shaped output
        return ChatCompletionResponse(
            choices=[ChatChoice(
                index=0,
                message=ChatMessage(role="assistant", content=resp.content[0].text),
                finish_reason=resp.stop_reason,
            )],
            model=resp.model,
        )

# log it
with mlflow.start_run():
    mlflow.pyfunc.log_model(
        artifact_path="agent",
        python_model=MyAgent(),
        pip_requirements=["anthropic"],
    )
A query is slow: SELECT * FROM metrics WHERE run_uuid='X' AND key='loss' ORDER BY step. Diagnose.

Likely missing or unused composite index on (run_uuid, key, step). EXPLAIN ANALYZE will show seq scan or wrong index. Fix: add CREATE INDEX CONCURRENTLY idx_metrics_run_key_step ON metrics (run_uuid, key, step). Validate with another EXPLAIN. If the table is huge and writes are heavy, consider partitioning by run_uuid hash or by time. If the result set itself is large (100k points), the bottleneck may be transfer — add downsampling at the API layer.

You've enabled tracing in production and the tracking DB is doubling weekly. What do you do?

Short term: (1) turn sampling on — 100% errors, sample successes; (2) shrink span attributes — drop verbose payloads. Medium term: (3) move trace storage off the same Postgres into a dedicated store with a TTL (object-storage-backed cold tier, or a time-series DB); (4) prune span content older than retention while keeping headers. Strategic: (5) audit which spans are high-volume and ask whether they're observable enough as aggregate metrics rather than per-call spans.

10. Recommended study path

  1. Read the source map. Skim mlflow/tracking/, mlflow/store/, mlflow/models/, mlflow/pyfunc/, mlflow/tracing/, mlflow/gateway/, mlflow/evaluation/. You don't need to read every file — read the __init__.py and any abstract*.py.
  2. Run the five-minute path. Locally with FileStore. Then with Postgres. Then point at S3/MinIO for artifacts. Each switch teaches a layer.
  3. Wrap a sklearn model and a ChatModel. Same registry, same scoring server, different signatures. Feel the unification.
  4. Turn on auto-tracing for one SDK (OpenAI, Anthropic, or LangChain). Read the resulting trace in the UI. Trace your own function with @mlflow.trace.
  5. Build a 30-row eval set. Run mlflow.evaluate with one heuristic judge and one LLM-as-judge. Inspect the assessments-to-trace linking.
  6. Read the architect guide (link) end to end. Each roundtable is a question someone is going to ask.
  7. Mock-interview yourself with the system design prompts. Time-box. Compare against the outlines.
  8. Find the corner cases. What happens if you call log_metric after end_run? What if two processes write to the same FileStore? What if the artifact backend is briefly unreachable? The interview will go here.
Final thought

Senior platform interviews are hardly ever "do you know the API" — they're "can you defend a design choice when challenged." Practice the second answer to every question, not the first. The first answer shows you read; the second shows you understood.
