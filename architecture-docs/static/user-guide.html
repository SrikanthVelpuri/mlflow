2. The five-minute path

The minimum viable workflow that you should be able to run before you read anything else.

# 1. point at a server (or skip and use ./mlruns locally)
export MLFLOW_TRACKING_URI=https://mlflow.your-company.internal

# 2. set the experiment — pick a stable name; runs cluster under it
mlflow.set_experiment("churn/v2")

# 3. wrap your training in a run; log signature + input example
with mlflow.start_run(run_name="rf_baseline"):
    mlflow.log_params({"n_estimators": 200, "max_depth": 8})
    model = train(...)
    mlflow.log_metric("auc", 0.87)
    mlflow.sklearn.log_model(
        sk_model=model,
        artifact_path="model",
        signature=infer_signature(X_train, model.predict(X_train)),
        input_example=X_train.head(3),
    )

# 4. promote — only register what you'd defend in a review
mlflow.register_model("runs:/{run_id}/model", "churn-classifier")
client.set_registered_model_alias("churn-classifier", "champion", version=4)

# 5. consume — never hardcode versions in prod code; use the alias
model = mlflow.pyfunc.load_model("models:/churn-classifier@champion")
If you only do five things

(1) Set an experiment name. "Default" is the path to chaos. (2) Always pass a signature. (3) Use aliases, not version numbers in consuming code. (4) Tag your runs with the data version, the git SHA, and the owner. (5) Don't log datasets as artifacts — log a Dataset reference.

3. Tracking — best practices

Run hygiene

  • One concept per experiment. "churn/v2/feature-engineering" is fine; "experiments-jan" is not.
  • Run names are for humans. Encode the change, not the timestamp: "add-aci-feature", not "run_2026_05_06_v2".
  • Tags carry context the run can't reconstruct: git_sha, dataset_version, trigger (manual / nightly / pr-check), owner.
  • Log params before training. A failed run with no params is a forensic dead-end.

Metrics

  • Step matters. Pass step=epoch so the UI draws curves.
  • Use log_metrics({...}, step=...) to batch a dict in one call. The async queue is good but fewer calls is better still.
  • Don't log a metric per row of validation — that's what the eval harness is for. Aggregate first.

Datasets, not files

Use mlflow.data wrappers (from_pandas, from_huggingface, from_spark, etc.) and mlflow.log_input(dataset, context="training"). The digest is content-hashed, so identical data across runs collapses — your storage bill thanks you and lineage queries actually work.

Common mistake

People log_artifact("train.csv") on every run, copying the same 2GB CSV into S3 N times. Use a Dataset reference; if the file truly is the source of truth, log it once and reference it by URI.

4. Packaging — best practices

  • Always pass signature= and input_example=. Signature lets the scoring server reject bad payloads with a 422; input_example lets the UI show a "predict" button.
  • Pin your environment. If you don't pass conda_env= or pip_requirements=, MLflow infers — and the inference can be wrong on niche packages. Pin explicitly for production.
  • Don't log the model from the notebook the data scientist trained in if you can re-train in a CI job that captures git SHA + locked deps.
  • Use code_paths= for custom Python modules the model imports, otherwise loading in another container will ImportError.
  • One model artifact, one purpose. Don't pack a feature transformer and a model in the same artifact unless they always deploy together — if you need to update one without the other, split.

5. Registry workflows

Champion / Challenger with aliases

# promote
client.set_registered_model_alias("churn", "challenger", version=12)
# run shadow / A-B
# if metrics hold:
client.set_registered_model_alias("churn", "champion", version=12)
# the previous champion alias automatically retargets — no copy

Code consumers always do models:/churn@champion. They never know what version is current. The promotion is a metadata flip, not a redeploy.

Region- and tier-specific aliases

Aliases are arbitrary strings. eu-prod, us-prod, internal-only, shadow, canary are all valid. The deployment pipeline reads its own alias, so a regional rollback only changes one alias.

Why this is good

Promotion is observable (alias changes are auditable), reversible (re-point), and decoupled from deployment (the running pod doesn't change). When something goes wrong at 2am, "flip the alias back" is the fastest rollback.

What to put in version description & tags

  • Description: the why — "rolled in zip-code one-hot, fixed leak from last_login".
  • Tags: data_version, git_sha, training_run_id, approved_by, compliance_review_id.

6. Projects & reproducibility

Use MLproject for the inner loop — "I want CI to be able to re-run my training". Use Airflow / Prefect / Argo / Dagster for the outer loop — "every Sunday, refresh + retrain + redeploy". They aren't competitors, they're nested.

# MLproject
name: churn-training
python_env: python_env.yaml
entry_points:
  main:
    parameters:
      data_uri: {type: str}
      n_estimators: {type: int, default: 200}
      max_depth: {type: int, default: 8}
    command: "python train.py --data {data_uri} --n-est {n_estimators} --depth {max_depth}"
Reproducibility is a chain

Reproducibility = pinned env + pinned code + pinned data + pinned hyperparameters. Miss any link and reproducibility is theatre. MLproject covers env + code + params; Dataset with a digest covers data; everything else is up to you.

7. AI tracing — best practices AI

  • Enable autologging for the SDKs you use: mlflow.openai.autolog(), mlflow.anthropic.autolog(), mlflow.langchain.autolog(). One line, free observability.
  • Use the @mlflow.trace decorator on your own functions to make custom span trees. Pass span_type="TOOL" / "RETRIEVER" / "AGENT" for typed spans the UI knows how to render.
  • Tag traces with request context: user_id, session_id, route, experiment_variant. Use mlflow.update_current_trace(tags=...).
  • Don't include PII in span attributes unless your store is approved for it. Mask early — at the trace boundary.
  • Sample in production. 100% trace capture for a high-QPS LLM service is a lot of bytes. Set up a sampler that always captures errors, samples a percentage of successes.
Roundtable — How much should we trace?
G AI Engineer
Capture 100% in dev and staging. In prod, target 100% of errors, 100% of low-confidence, sample 5-10% of nominal traffic. The trace is most valuable on the calls that misbehaved.
P PM
For specific user-facing features I want 100% capture so we can debug individual user complaints. The cost is the price of a usable feedback loop.
X Security
If span content includes user input, treat the trace store like the chat history — same retention, same encryption, same right-to-delete plumbing.
D Storage
Span tables grow faster than you think — ours doubled the metric table within two months of enabling traces. Plan TTL or cold-tier off-load from day one.

8. AI evaluation — best practices AI

  • Build the eval set before the agent. If you can't write 30 examples of "right answer", you don't know what the agent should do.
  • Mix judge types. Heuristic checks (regex, JSON validity, contains-keyword) are cheap and deterministic. LLM-as-judge for nuance. Human-rated golden set for calibration.
  • Calibrate the judge. Sample N rows, have humans rate, measure judge-vs-human agreement. If < 80% agreement, your judge prompt needs work — not your agent.
  • Run eval on every PR that touches the agent. Treat regressions like test failures.
  • Make assessments addressable. Tag the row with the test case ID so you can trace eval-failure-row → agent-trace → judge-trace in one click.
The closed loop

Production trace → sample interesting failures → add to eval set → eval catches the regression next time. Without the loop, your eval set staleness becomes your model's blind spot.

9. Agents in production AI

  • Wrap as a ChatModel early, even if you're prototyping. The discipline of declaring inputs/outputs as ChatMessage/ChatParams pays off the first time anything talks to it.
  • Cap iterations. Every agent loop needs a hard limit. "I'll trust the LLM to terminate" is how you discover a $400 trace.
  • Cap latency. Long-tail user requests are worse than failed ones. Time-bound the whole agent and gracefully partial-respond.
  • Idempotent tools. If the agent retries, the tool must not double-charge / double-send / double-write.
  • Route through the AI Gateway. Even single-provider apps benefit from centralised keys, rate limits, and per-team cost attribution.
  • Trace + evaluate. Every prod path should be traceable; every traced agent should have an eval set.

11. Stakeholder map

The platform serves more than its primary user. Each role has different success criteria; conflict is normal, not pathological. Naming the conflict is most of the work of resolving it.

Data Scientist

Wants: velocity, notebook freedom, easy comparison, no friction to log.

vs. ML Engineer's "your code must be packaged".

ML Engineer

Wants: reproducibility, signed artifacts, CI gates, predictable promotion.

vs. Data Scientist's "I just want to ship this".

AI Engineer

Wants: fast prompt iteration, end-to-end traces, eval-as-CI.

vs. SRE's "what's the p99?".

Product Manager

Wants: features shipped, business KPIs visible, predictable timelines.

vs. ML Engineer's "the eval set isn't ready".

SRE / Platform

Wants: SLOs met, blast radius limited, no surprise spend.

vs. AI Engineer's "I need to A/B four prompts in prod".

Security & Compliance

Wants: auditable provenance, no PII leakage, key rotation, RBAC.

vs. Data Scientist's "can I just put my key in .env?".

Finance / Cost

Wants: per-team attribution, budgets enforced, predictable spend.

vs. PM's "the demo needs GPT-4".

Legal / Risk

Wants: approved providers only, model risk documented, decisions explainable.

vs. AI Engineer's "the new model is 30% better on our eval".

12. Tradeoff roundtables

How much process for promotion?

DS velocity vs production discipline
N Data Scientist
Every promotion needs three approvals, a signed-off eval, and a 24-hour shadow. By the time I'm in prod, the data has shifted again.
M ML Engineer
Last month a model went out without a signature and broke 4% of requests for two hours. Process is the residue of that incident.
P PM
What if process scales with blast radius? Internal-only models: lighter approval. User-facing: full ladder. Same alias mechanism, different gates.
S SRE
Tier the approvals by alias. Promoting to shadow: anyone. challenger: team lead. champion: + on-call sign-off. The platform enforces it via alias-write RBAC.
A Architect
That's the resolution. The bureaucracy is proportional to risk; the platform encodes the policy; nobody negotiates per-deploy.

Self-service vs guard-rails for LLM provider choice

Should every team pick its own LLM provider?
G AI Engineer
Different products want different providers — Claude for long-context, GPT-4 for tools, a small open model for cheap classification. Locking us to one provider hurts the product.
X Security
Each provider is a separate vendor risk review, DPA, key rotation surface, audit log to wire up. We can't have N teams onboarding N providers ad-hoc.
A Architect
The gateway is the answer. Approved providers behind one URL; teams pick from the menu, not from the open internet. New providers go through one approval flow, then everyone benefits.
P PM
The menu has to actually update. If "approved providers" lags six months behind the frontier, teams will route around the platform. A monthly review, not a yearly one.

Cost vs quality on the inference path

Who picks the model — the engineer, the PM, or the bill?
P PM
User-facing quality is the metric that matters. If the bigger model wins eval by 8 points, we ship it.
G AI Engineer
8 points on which slice? On 60% of traffic the small model is indistinguishable. Route by complexity: small model first, escalate on low confidence. We've cut cost 4× that way.
A Architect
Routing logic belongs in the agent, not in the gateway. The gateway is a meter; the agent makes the call. Trace both legs so we can see when the small model wins.
S SRE
And budget alarms per route — when the spike lands at midnight, I want to page the PM, not me.

Auth, RBAC, and the data-science notebook

How locked-down should tracking be?
N Data Scientist
If logging a metric requires a service principal token rotated every 7 days, I will stop logging metrics.
X Security
If an unauthenticated user can write to the tracking server, anyone on the corp network can poison runs.
A Architect
SSO at the proxy, refresh tokens cached locally, MLflow client picks up MLFLOW_TRACKING_TOKEN. No daily logins, no hand-rolled credentials in notebooks.
S SRE
And per-experiment write ACLs as the second line. Even if a token leaks, blast radius is one team's experiment.

13. Scenarios

Scenario
"We need to ship a new RAG agent in two weeks."

Platform side: spin a ChatModel, register it under a clear name, point a shadow alias at it, route it through the gateway. Wire mlflow.openai.autolog() + your retriever's @mlflow.trace. User side: seed a 50-row eval set from existing user questions; pick three judges (retrieval-relevance, answer-faithfulness, JSON-shape). Gate every PR on the eval. Stakeholder balance: PM gets a Friday demo URL (the shadow alias resolves through the gateway); SRE gets the iteration cap and time budget; security gets the audit trail (every call traced through the gateway). When eval clears, flip the alias to challenger, then champion.

Scenario
"Our tracking DB hit 100M rows and queries are slow."

First check: the metrics table indexes — (run_uuid, key, step) should be present. Next: archive runs older than retention to a cold experiment (or a separate read-only DB). Stakeholder balance: DS may push back on archive ("I might need that 2023 sweep"); compromise is to keep run metadata, archive metric history, and ship a one-line API to rehydrate on demand.

Scenario
"PM wants A/B in prod; SRE doesn't want surprise traffic to a new model."

Use two aliases (champion, challenger) and a deterministic split at the gateway. Track variant as a trace tag. The gateway enforces the split; SRE's traffic graph stays clean; PM gets the A/B. If the challenger underperforms on a key business metric, flip the alias back. No code change.

Scenario
"Legal flagged GPT-4 for a regulated workflow; we need to switch providers."

The workflow already routes through the gateway, so the change is a route swap to an approved provider (Bedrock with a regional model, perhaps). Re-run the eval set; if it passes, flip. The agent code does not change. This is exactly the property the gateway is bought for.

Scenario
"Data scientist wants to log 10,000 metrics per training step."

Don't. The per-step metric is a curve; 10,000 of them is 10,000 curves, which is an artifact, not a metric. Aggregate (mean, p50, p95) into a handful of curves; log the full per-feature distribution as a single artifact (e.g. a Parquet file or a histogram image) that the comparison view can render. The async queue will keep up technically; your future self looking at the UI will not.

15. When to escalate

  • Anything affecting prod inference — broken signature, registry alias pointing at a deleted version, gateway 5xx storm. Page the on-call before you investigate.
  • Cost anomalies — gateway cost or trace storage growing > 2× week-over-week without a known cause.
  • Security signal — suspected key leak in a notebook, PII in a span attribute, unauthorised alias write.
  • Compliance change — new regulation, new approved-provider list, new data residency requirement. Loop in legal & the platform team before code changes.
  • Cross-team conflict that's blocking a launch — bring it to the architect roundtable rather than DM-fighting it. Most of these are not technical disputes.
The meta-rule

The platform exists so the same five primitives (six, with traces) work for everyone. When you find yourself fighting the platform — building parallel systems, hiding state in tags, hardcoding around aliases — that's a signal to escalate, not work around. The architects want to know.
